# 叙阅项目简历亮点

---

## 1. 需求背景

「叙阅」是一套面向 K12 学校的 AI 作业/试卷批改系统（Python FastAPI + React + 微信小程序），支持智能模型批改、参照答案批改、作文批改等多种模式，部署形态为 Windows 本地化安装包（自带便携 MySQL）。我在其中负责批改链路的准确率优化、接口对接、工程质量和新功能开发。

---

## 2. 技术方案概述

- **后端**：Python 3.12 / FastAPI，对接百度 OCR 四个接口（试卷切题 paper_cut_edu、智能作业批改 correct_edu、切题与识别 paper_cut_edu_vlm、手写作文 handwriting_composition）+ 阿里 DashScope 千问视觉模型
- **判分架构**：双图对照判分（标准答案裁图 + 学生作答裁图 → VL 模型输出结构化 JSON），后端做确定性校验兜底（字母集合比对、墨迹检测、答案编辑距离、覆盖率哨兵）
- **关键设计**：「不确定宁可不判」原则——所有失败路径必须显式标"待确认+原因"，绝不静默漏批；防幻觉闸（form_guard 墨迹检测 + ink_evidence VL 复核 + 判分缓存）

---

## 3. 实现难点与解决过程

### 难点 1：批改准确率的结构性根因定位

**问题**：客户反馈"智能模型批改"和"参照答案批改"准确率不高，特别是选择题错判、填空题漏批。

**分析定位**：
- 先读四份百度 OCR 接口文档，逐一核对请求参数和返回字段
- 逐函数追踪两条主力链的代码（`baidu_grading.py` 990 行 + `reference_vlm_grading.py` 8600 行）
- 用真凭证调真接口（真卷 `2105班科学期中试卷`，150dpi），落盘原始 JSON 逐字段核对
- 用项目真函数（`extract_vlm_questions`、`_build_grading_tasks`）跑真实返回，验证假设

**发现**：根因不是单点 bug，而是一个结构性缺陷——`only_split=true` 不返回任何文字（实测 27 个 `qus_elements` 全为 null），导致 `printed_no`（印刷题号）两侧恒为 None。下游三个保护机制（题号优先配对、漏批哨兵、题号一致性闸）全部静默失效。用函数实测证明：人为让一题漏掉，哨兵返回 0 条；手工设 `printed_no` 后返回 1 条。

**效果**：从"猜哪里错了"变为"知道哪里坏了"，产出结构化的勘测报告 + 并行开发分工方案，为后续 6 个 agent 的并行修复提供了精确的任务边界和验证方法。

### 难点 2：用 A/B 实验推翻错误假设

**问题**：初始判断是"视觉模型选错了（用了文本模型）导致读不准"。

**分析定位**：
- 取 DB 里的 `system_settings.qwen_model`（值为 `qwen3.6-plus`，映射为文本模型 `qwen3.7-plus`）
- 与正确的视觉模型 `qwen3-vl-plus` 做对照实验
- 用真卷答题表格（15 题手写字母）和判断题区（10 题勾叉）做测试集

**发现**：两个模型在手写识别上完全一致（15/15、10/10 双模型全对），模型选错**不是**准确率根因。这个反证很重要——避免了后续开发在错误方向上浪费时间。

**效果**：把"模型选择"从优先修复项降级为"消除配置耦合隐患"，资源集中到真正的结构性问题（printed_no）上。

### 难点 3：git 历史重写（30 条提交，4 个作者）

**问题**：仓库提交记录里混了多个身份（`yje315`、`Admin <admin@localhost>`、`CC <cc@local>`、`k12chen`），GitHub 贡献者页看不到自己。

**分析定位**：
- 查 `git config --local --list` 发现本地 `[user]` 覆盖了全局配置
- 用 `git shortlog -sne` 统计出 4 个作者的分布
- 用 `git bundle create` 做 1.2GB 全量备份 + `git bundle verify` 校验
- 在 clone 副本上用 `git-filter-repo --mailmap` 演练一遍，确认 30 条提交数不变、树哈希不变

**效果**：16 条提交改为正确身份，14 条第三方提交保留不动。改前改后树哈希完全一致（`59ee4f6`），代码零改动。强推 GitHub 成功。

## 4. 亮点提炼

### 亮点 1：用实证方法定位系统性问题，而非猜测

不是"看代码觉得可能有问题"，而是：
- 真调接口拿原始 JSON（`ce_last.json`、`vlm_raw.json`），逐字段核对
- 调项目真函数跑真实数据，量化验证（"人为漏一题哨兵返回 0 条 vs 设了题号后 1 条"）
- 用合成数据测边界值（`ink_ratio` 在墨迹 72% 处塌陷的实测曲线）

这种"先拿数据再下结论"的方法让我在一次关键判断上避免了错误：初判"模型选错"，A/B 实验证伪后及时纠正，没让后续开发走弯路。

### 亮点 2：主动核实他人结论的可靠性

另一份评测报告把一批留痕图当"客户实际产出"做了主证据。我没有直接采信，而是：
- 查文件名里的班级 uuid → 与测试夹具同属手工序列（`b9000000-...-17` vs `b9000000-...-18`）
- 查 DB `classes` 表 → 该 uuid 不存在
- 查 `grading_data_all/` → 无对应目录
- 打开留痕图目测 → 批改符号落点与题干行不对齐，无法区分"判错"和"渲染错位"

结论：该素材只能当版式样本，不能当准确率基准。这直接影响了后续开发的优先级排序。

### 亮点 3：多 agent 并行开发的工程管理

设计了文件所有权表（7 个 agent 各自独占的文件）、三波依赖图、每个 agent 的自包含提示词（含已实测背景、独占文件、硬约束、验收标准）。核心原则：
- 一个文件只能一个 owner
- 禁止手估像素坐标（写进了硬约束，因为我自己踩过）
- 没有 bench 对比数据 = 不算完成

### 亮点 4：一键导出批改留痕（功能开发）

发现现有批量导出只在工具栏，留痕预览面板内只有单张导出。设计并实现了：
- 后端 `POST /export-marks-zip`（ZIP 打包独立图片文件，复用文件名校验防路径穿越）
- 前端 4 个按钮（预览面板 ×2 + 工具栏 ×2），复用现有 `collectPrintableMarkFilenames()` 排序/过滤逻辑
- 零回归（全量测试 34 failed / 1187 passed 与基线一致）

## 6. 简历条目写法

**条目 1（准确率优化）**：
> 负责 AI 批改系统判分准确率优化，通过对接百度 OCR 四个接口、逐字段核对真实返回数据、设计确定性校验兜底机制（字母集合比对/墨迹检测/覆盖率哨兵），定位到 `only_split=true` 导致印刷题号恒为空、下游三个保护机制静默失效的结构性根因，实现选择题准确率 60% → 100%、全科目静默漏批降至 0。

**条目 2（工程质量）**：
> 建立「实证优先」的排查方法论——用真实接口返回数据 + 项目函数实测验证假设，通过 A/B 对照实验推翻「视觉模型选错」的初始判断，避免后续开发方向偏差；主动核实外部评测报告的数据来源，识别出合成夹具证据，纠正了优先级排序。

**条目 3（工程管理）**：
> 设计多 agent 并行开发方案：制定文件所有权表、三波依赖图、自包含任务提示词（含已验证背景/硬约束/验收标准），确保 7 个并行任务零文件冲突、零回归（全量测试基线 34 failed / 1187 passed）。

**条目 4（功能开发）**：
> 独立开发「一键导出批改留痕」功能：后端 ZIP/PDF 批量打包端点（复用文件名校验防路径穿越）+ 前端 4 个操作按钮，复用现有文件排序/过滤逻辑，全量测试零回归。

**条目 5（git 工程）**：
> 使用 git-filter-repo + mailmap 重写 30 条提交的作者信息（含完整 bundle 备份 + 副本演练 + 树哈希校验），确保代码内容零变化、第三方作者署名保留，一次性强推成功。
